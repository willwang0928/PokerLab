# Calibration of the coach and the leak detector (v0.4.5)

This document describes how PokerLab's coaching and leak detection were evaluated
empirically, what was found, and what was changed. The generated numbers are in
[`calibration/report.md`](calibration/report.md) (raw: `calibration/results.json`).

Everything here is an estimate from simulation against PokerLab's own opponents. Nothing
is compared with game-theory-optimal play.

## Reproducing

```bash
cd backend
python -m pokerlab.calibration --stats-only   # synthetic statistics only (a few minutes)
python -m pokerlab.calibration --quick        # small end-to-end run (pipeline check)
python -m pokerlab.calibration                # full run: ~2 h on 8 cores, then the report
python -m pokerlab.calibration.bench          # scenario-generation benchmark
pytest -q tests/test_calibration.py           # fast checks of every piece of the harness
```

Simulated sessions are cached in `backend/.calibration-cache/<config hash>/`; re-running
only redoes the analysis. All randomness is seeded (default seed `20261112`), so a run
with the same code and configuration reproduces the same hands, grades and numbers. The
discovery run described below lives in `.calibration-cache/discovery-coach-v0.4.4/` and
can be regenerated by checking out the v0.4.4 coach (`git show v0.4.4:backend/pokerlab/coach/analysis.py`)
with the v0.4.5 harness.

### Storage and machine load

Measured: one simulated session is ~165 KB of JSON, so a full run (14 policies × 8
sessions) writes ~20 MB; the report pass from a warm cache writes only `report.md` and
`results.json` (~0.3 MB) and peaks at ~560 MB of RAM across its worker processes
(~50 MB per simulation worker). Nothing grows during a run except the session files, and
the cache only gains a folder when the configuration changes.

- **Disk guard.** A run refuses to start unless its estimated output fits with
  `POKERLAB_MIN_FREE_MB` (default 1024) still free, and re-checks after every session,
  stopping cleanly (finished sessions stay cached and are reused) instead of filling the
  disk. The reserve is deliberately much larger than the output: on macOS, swap files
  live on the same disk and appear and disappear in 1 GB steps under memory pressure.
- **One run at a time.** A lock on the cache directory (`.lock`, released by the OS if
  the process dies) refuses a second calibration or `diagnose` run on the same cache.
- **Interrupted runs.** Sessions are written to `*.tmp` and renamed when complete;
  leftovers from an interrupted run are deleted when the next run starts.
- **Cleanup.** `python -m pokerlab.calibration.housekeeping` lists the cache and what is
  stale; `--clean` removes folders for configurations no longer in use and partial files,
  keeping the current full and `--quick` configurations and the discovery run; `--all`
  removes everything (re-simulated on the next run). The cache is git-ignored.

## What is measured, and against what

Three layers are kept apart, because a single "accuracy" number would mix them:

1. **The detector's statistics** (`pokerlab/calibration/stats_eval.py`). Synthetic
   decisions whose flags are drawn with a *known* probability go straight into the leak
   detector. The true flagged rate is known exactly, so false-positive rates and power
   can be measured precisely and cheaply, independently of the coach.
2. **Detection of injected tendencies** (`policies.py`, `simulate.py`). Simulated
   players with deliberately injected behaviour play the real engine against the real
   opponents; the real coach grades every decision; the hands become real history
   records; the real leak detector reads them. Ground truth here is *what was injected*.
3. **Whether the coach's judgements are strategically right** (`oracle.py`). An
   independent oracle plays the rest of each hand out many times from the exact state of
   a decision, with both players' real cards and the true policies, after the chosen
   action and after an alternative. The difference in final stacks estimates what the
   decision actually cost against this opponent, over every later street. It uses
   nothing the coach computes: no range model, no fold model, no one-street cut-off.

Ground truth is never defined by the coach's own judgements. An injected deviation is a
behavioural fact, not a proven leak: "calls more often than the baseline" is only a
weakness if those calls lose chips, which the oracle measures. Detection is therefore
reported twice: against injected tendencies, and against weaknesses the oracle
confirms.

### Simulated players

Every policy is the PokerLab Intermediate opponent logic (a reasonable heuristic, not an
optimal strategy) plus zero or more injected deviations. A deviation fires only in its
condition, with a fixed probability, and replaces the action the baseline logic chose;
every decision records the baseline action and which deviation fired. Deviations use
only what the player can see.

| policy | injected behaviour |
|---|---|
| `baseline` | none |
| `baseline_vs_changing_opponent` | none; the opponent switches from Beginner to Advanced halfway |
| `beginner_style` | the Beginner logic: weaknesses that emerge rather than being injected |
| `calling_station` | calls 70% of the postflop bets the baseline folds |
| `river_station` | the same, on the river only (85%) |
| `big_bet_station` | the same, facing bets of ¾ pot or more only (85%) |
| `over_folder` | folds 55% of the postflop bets the baseline calls |
| `over_bluffer` | bets ⅔ pot with no made hand 65% of the time the baseline checks |
| `never_bluffs` | never bets or raises without a made hand (no detector category exists for this) |
| `slow_player` | checks or calls 75% of the time the baseline bets or raises with two pair or better |
| `preflop_loose` | calls 70% of the preflop raises the baseline folds |
| `station_and_bluffer` | two tendencies at once |
| `station_then_fixed` | calls too much for the first half of the run only |
| `random` | uniformly random decisions |

Each policy plays 800 hands in sessions of 100 (opponents and the coach's opponent model
start fresh each session), with stacks drawn from 25, 50, 100 and 150 big blinds so that
stack-depth conditions occur. Decisions are graded by the production coach (4,000
samples, range check on).

### The oracle

From the state at a decision, the hand is played out `R = 12` times after the chosen
action and after the alternative, with paired randomness (same run-out, same agent
draws), and the player keeps playing their own policy afterwards. For a flagged decision
the alternative is the option the coach preferred; for an injected deviation it is the
action the baseline would have taken; for a control sample of decisions graded good it
is the best other option. Up to 30 decisions per session and kind are evaluated, chosen
uniformly at random, and weighted back to the full set. Results are mean big blinds per
decision with a 95% interval; a verdict (*costly* or *gains*) needs the interval to
exclude zero and at least 15 evaluations.

A single evaluation is noisy, but averaged over many decisions the opponent's hands are
drawn from their true distribution at that point, so the mean is an unbiased estimate
of the cost of that kind of decision as made by that player, against that opponent.

### Detection by sample size

For each policy and each sample size N (50 to 800 hands), whole hands are resampled
with replacement from the policy's 800 (100 bootstrap replicates), and the detector is
run on each sample. This keeps the dependence between decisions of the same hand. At N
close to 800 the samples largely repeat the pool, so those estimates inherit its quirks.

## Findings

### 1. The v0.4.4 statistics produced false findings (fixed)

On synthetic data with known rates (report §1, 1,000 replicates per cell), the v0.4.4
detector:

* reported **at least one false leak in 30–37%** of histories where six kinds of
  decision all sat exactly at the 15% threshold: eight weaknesses were tested on every
  report with no multiple-testing correction;
* named a **"concentration" in about half of all detected leaks when none existed**:
  each of ten conditions compared the 95% lower bound inside with the *point* rate
  outside, ignoring the outside sample's uncertainty, and the conditions were not
  corrected for multiplicity;
* treated decisions from the same hand as independent: with strongly correlated
  decisions (three per hand, intra-class correlation 0.6) the false-leak rate at the
  threshold rose from about 5% to about 13%;
* labelled a weakness *possible* whenever two decisions were flagged, however low the
  rate: 6 flagged out of 160 (3.75%) was shown under "too early to tell" rather than as
  evidence against a leak;
* used a normal-approximation two-proportion test for trends with as few as 8 decisions
  per side.

v0.4.5 replaces these with an exact binomial test and Clopper–Pearson interval on an
effective sample size (design effect estimated from within-hand clustering, never below
1), Benjamini–Hochberg at 5% across the weaknesses tested on a report, one-sided Fisher
exact tests with Benjamini–Yekutieli at 10% for conditions (valid when conditions are
complementary and so negatively dependent), two-sided Fisher exact tests for trends,
and a *possible* status only while the interval still reaches the threshold. The same
synthetic streams give (v0.4.4 → v0.4.5): any false leak with six kinds at the threshold
**37% → 3%** (n = 40) and **30% → 3%** (n = 160); spurious concentration **53% → 3%**
(n = 40) and **48% → 2%** (n = 160); false leaks with correlated decisions **13% → 3%**.
A true river concentration is still found 99% of the time (v0.4.4: 100%). Power is kept
for clear leaks (a 25% rate over 160 opportunities: 94% → 92%; over 80: 73% → 73%) and is
lower for small samples (a 25% rate over 20 opportunities: 40% → 23%), the price of exact
tests at small n. A clean record now needs 24 confidently graded decisions to count as a
strength (0 flagged of 20 is not yet significant), and a 5% flagged rate over 160
decisions is a strength 94% of the time (v0.4.4: 0%, because it was shown as *possible*).

Why Benjamini–Hochberg and not Bonferroni: the question a player asks is "which of these
findings are real", and BH controls the expected share of false ones; with no real
weakness at all it bounds the chance of *any* false leak by the same 5%. BH assumes
independent or positively dependent tests; the weaknesses either use disjoint decisions
or share decisions (a call is an opportunity for two kinds), which is positive
dependence. Conditions within one leak can be negatively dependent (river versus the
other streets), so they use the more conservative Benjamini–Yekutieli procedure.

**Repeated looks remain a limitation.** The report is recomputed after every hand. For
one weakness exactly at the threshold, re-checking every 5 hands over 300 hands reports
it at some point in about 17% of histories (v0.4.4: 22%); at a true 10% rate, about 1%
(v0.4.4: 2%).
An alpha-spending scheme would fix this but makes findings depend on the whole history
of looks; instead the interface says that a finding near the threshold can appear and
disappear as hands are added.

### 2. The coach was wrong about raises facing a bet (fixed)

The discovery run graded the simulated players with the v0.4.4 coach and evaluated
3,500 of its flags and controls with the oracle (report, "Discovery run"). Findings:

| what the coach said (v0.4.4) | oracle Δ bb per decision, 95% | coach's own Δ |
|---|---|---|
| calling without the odds (all confidences) | **−10.7 ± 1.2**: confirmed costly | −6.8 |
| high-confidence flags (all kinds) | **−10.3 ± 2.0**: confirmed | |
| medium-confidence flags | **−6.8 ± 2.3**: confirmed | |
| low-confidence, range-dependent flags | −5.7 ± 2.7 | |
| **low-confidence flags that held for every range** | **+2.9 ± 0.8: the player's choice did better** | |
| **"folded with the odds"** | **+5.9 ± 2.8: folding did better** | −5.2 |
| flags with no tag (mostly "should have raised") | **+5.3 ± 1.4: the choice did better** | −3.2 |
| "missed value" | −0.2 ± 1.2: not confirmed | −3.0 |
| decisions graded good (control: chosen vs best other option) | +0.5 ± 0.5 (low), +0.5 ± 0.6 (medium), +0.5 ± 1.9 (high): not worse | |

Broken down by the pair of actions compared:

| chosen instead of the coach's preference | n | oracle Δ bb | coach Δ bb |
|---|---|---|---|
| call instead of fold | 478 | **−10.5 ± 1.2** | −6.5 |
| call instead of raise | 548 | **+4.2 ± 1.5** | −2.8 |
| fold instead of raise | 160 | **+4.4 ± 3.3** | −3.8 |
| fold instead of all-in | 41 | +12.3 ± 8.6 | −10.7 |
| call instead of all-in | 81 | +3.2 ± 2.6 | −7.6 |
| fold instead of call | 103 | **+3.4 ± 2.4** | −2.9 |
| check instead of bet | 335 | **−1.1 ± 0.9** | −2.1 |
| bet instead of check | 86 | +2.3 ± 2.4 | −2.5 |

Almost all of the wrong flags were one thing: **facing a bet, the coach preferred a raise
valued only by its fold model** (minimum-defence fold frequency) over a call or fold that
was sound on pot odds. Many of those folds were also *tagged* "folded with the odds"
although calling itself was not profitable, so the tag described something untrue. The
PokerLab opponents fold far less to a raise than the minimum-defence model assumes:
their betting range is already strong. The second, smaller error: "you should have called
instead of folding" verdicts before the river leaned the wrong way (+3.4 ± 2.4 bb), with
too few cases per confidence level to say more; folded hands are usually weak and realise
less of their equity than the 70% the coach allowed for.

Fixes:

* Facing a bet, a call or fold that is best on pot odds is no longer graded down because
  a fold-model raise scores higher. It is a "close call", and the raise is shown as an
  option resting on an assumed fold rate ("not the answer"). A fold is therefore only
  tagged "folded with the odds" when the call itself paid, and its explanation no longer
  says "that is enough to continue" when it was not.
* A fold before the river is a confident verdict only if calling would pay even when
  realising 50% of its equity (70% before); between 50% and 110% it is a judgement call
  (low confidence, never a leak on its own).
* Training never teaches a fold-model raise as the answer to a facing-a-bet scenario.
  Scenario ids move to `v3`; `v1`/`v2` ids still load with the current generator and keep
  their id. Because draws often had a raise as the best answer, the generator now tries
  up to 240 candidates (80 before); at Intermediate and Advanced about 1 seed in 10 still
  finds no scenario, and the app retries once with a new seed.
* Bets when checked to are unchanged: there the fold model's recommendations held up,
  modestly (check instead of bet: −1.1 ± 0.9 bb).

Other coaching findings:

* **The coach understates what bad calls cost** before the river (medium confidence:
  coach −3.0 bb, oracle −11.7 ± 2.2 bb for the same decisions): calling now leads to more
  calls later. The direction is right; the size is a one-street estimate, as labelled.
* High-confidence verdicts are both right and well sized (coach −10.3, oracle
  −10.8 ± 2.1 bb for high-confidence calls without the odds).
* After an all-in call the coach still showed the "one-street estimate, ignores later
  betting" caveat although no betting can follow; removed.
* Low-confidence verdicts were displayed with the same chips as confident ones
  ("Questionable", "Good"); they now read "Possibly questionable" and "Looks
  reasonable".

### 3. Injected tendencies are not all leaks

The oracle priced each injected deviation against the baseline action it replaced:

| injected tendency | Δ bb per occurrence | verdict |
|---|---|---|
| calling too much after the flop | −8.1 ± 1.3 | costly |
| calling too much on the river | −5.4 ± 1.7 | costly |
| calling too much (with also bluffing too much) | −11.8 ± 3.0 | costly |
| folding too much after the flop | −0.9 ± 3.9 | no clear cost |
| bluffing too much (⅔ pot with no made hand) | −0.2 ± 0.9 | no clear cost |
| never bluffing | −0.8 ± 1.5 | no clear cost |
| slow-playing two pair or better | +1.2 ± 2.4 | no clear cost |
| defending too wide preflop | +0.1 ± 1.2 | no clear cost |
| random play | −0.8 ± 1.8 per decision | no clear cost per decision |

Against these opponents only *calling too much* is a demonstrated leak. A detector that
reported the other injected tendencies would be reporting behaviour, not costly play;
the leak detector reported them rarely or never, which is what the oracle supports.
`big_bet_station` almost never triggered (4 deviations in 800 hands: the baseline seldom
folds to large bets), so it says nothing either way.

### 4. Training improvement: what can and cannot be claimed

Before v0.4.5, practice scores mixed answers to scenarios seen before, practice on the
player's own hands (whose review they had already read) and genuinely new scenarios,
and the Auto difficulty raised the level as the player improved, which lowers the raw
score. The new evaluation (`pokerlab/coach/evaluation.py`, shown as "Is practice
working?" on the Progress tab):

* classifies each first answer as *new* (a generated scenario answered for the first
  time; seeds come from a space of a billion, so these are held out), *repeat*, or
  *own hand*;
* judges improvement on new situations only, comparing the earlier and later half within
  each (concept, difficulty) stratum with the Cochran–Mantel–Haenszel test (two-sided,
  5%) and reporting the Mantel–Haenszel pooled difference;
* shows familiar situations separately ("these can be remembered, so they are not
  counted as evidence of skill") and table decisions before and after the first practice
  separately, worded as a before-and-after comparison that cannot show cause;
* says "still evaluating" below 20 new answers.

Validated against simulated learners with fixed seeds (`tests/test_training_eval.py`): a
memoriser who improves only on repeats is reported as "no clear change"; a genuine
learner (35% → 85%) as improving; a player whose skill is constant but who moves from
Beginner (80%) to Advanced (50%) is not reported as declining although the raw rate
falls; a player who does not change is reported as changing in at most 6 of 60 seeds
(nominal 5%). The CMH statistic matches a hand computation.

This is still observational: no control group, and the player chooses when and what to
practise. PokerLab can report that answers to new situations improved; it does not claim
that practice caused it. Scores measure agreement with PokerLab's own analysis.

### 5. Scenario generation performance

Profiling showed 88% of generation time in exact equity enumeration (`equity._exact`),
and that the "quick" screening pass (600 samples) used exact enumeration whenever the
engine allowed it (up to 600,000 evaluations), so on the flop it cost as much as the full
pass. Screening now uses Monte Carlo above 20,000 evaluations; the full pass that decides
and grades the scenario is unchanged (same seeds, same samples, same exactness).

Benchmark (`python -m pokerlab.calibration.bench`, `calibration/benchmark.json`; 3 seeds
for each of 21 concept/level cells; measured while the calibration simulation occupied
every core, so absolute times are inflated and only the ratios are meaningful): the sum
of the 21 median times fell from 306 s to 91 s; drawing hands 92 → 9 s (Intermediate) and
74 → 9 s (Advanced); "Opponent tendencies" 31 → 4.4 s (Beginner) and 42 → 6.9 s
(Advanced); some cells were no faster or slightly slower (Intermediate bet sizing 12 →
17 s). 58 of 63 seeds produced exactly the same scenario; the other five produced a
different scenario that passes the same full checks. Correctness checks (legal
actions, range-robust answers, hidden-information safeguards, reproducibility from the
id) are the existing training tests, all passing.

The v3 rule (no fold-model raise as the taught answer facing a bet) rejects more draw
spots: at Intermediate and Advanced about 1 seed in 10 for drawing hands still finds no
scenario within 240 candidates, and those requests take longest. The app retries once
with a new seed.

### 6. After the fixes: the v0.4.5 coach and detector on the same players

The full run (report §2–§4) regrades the same simulated hands with the v0.4.5 coach and
re-evaluates its flags with the oracle.

**What the fixes changed (oracle Δ bb per flagged decision, 95%):**

| flags | v0.4.4 coach | v0.4.5 coach |
|---|---|---|
| call instead of the coach's raise | 548 flags, **+4.2 ± 1.5** (choice did better) | 79 flags, **+7.1 ± 4.1** |
| fold instead of the coach's raise | 160, **+4.4 ± 3.3** | 80, −0.3 ± 4.7 (no clear error) |
| "folded with the odds" | 250, **+5.9 ± 2.8** | 135, +0.9 ± 3.4 (no clear error) |
| low-confidence flags that held for every range | 1,192, **+2.9 ± 0.8** | 602, +0.6 ± 0.9 (no clear error) |
| calling without the odds | 456, −10.7 ± 1.2 | 487, −10.6 ± 1.2 (confirmed) |
| "missed value" | 543, −0.2 ± 1.2 | 344, **−1.3 ± 0.9** (now confirmed, modestly) |
| decisions graded good (control) | not worse at any confidence | not worse at any confidence (high −0.2 ± 1.6) |

The raise-facing-a-bet error is mostly gone: such flags fell by 86%, and the categories
that leaned the wrong way are now indistinguishable from zero. **Three weaknesses remain
and are open** (not fixed in v0.4.5; they are the starting point for v0.4.7):

* **"Overaggressive" river bets** (bet where the coach preferred a check): the bet did
  better, +2.4 ± 2.2 bb over 79 flags (coach's own estimate −2.7). This rule was not
  changed in v0.4.5; in the discovery run the same flags were +2.6 ± 2.8 (not
  significant) and the larger sample now makes the error clear. The coach's fold model
  for bets on the river underrates how often these opponents pay off.
* **Remaining "should have raised" flags facing a bet when the call itself was not
  profitable on pot odds** (mostly on the turn, untagged): +7.1 ± 4.1 bb over 79 flags.
* **"Fold instead of call" verdicts** still lean the wrong way overall (+2.3 ± 2.1 bb
  over 105), although the confidently tagged subset is now unclear (+0.9 ± 3.4).

None of these produce leak reports (the detector reported no overaggressive or
folded-with-the-odds leak for any policy at any sample size), but they do appear in
individual hand reviews.

**Leak detection on simulated players (v0.4.4 → v0.4.5 detector, both on v0.4.5 coach
grades, 800 hands):** precision against injected tendencies 84% → 84%; against
oracle-confirmed weaknesses 100% → 100%; false-positive rate 1.0% → 0.9%; recall 35% →
30% (injected) and 48% → 42% (oracle-confirmed). The `baseline` player was never
reported by either detector at any sample size, nor when re-checked every 25 hands.
The stricter statistics therefore **cost power on these players without a measurable
precision gain**: calling_station is found in 48% of 100-hand samples (v0.4.4: 77%),
river_station in 16% of 800-hand samples (33%), station_then_fixed in 37% (57%). The
synthetic worst case is what the stricter tests buy: with rates sitting at the threshold
v0.4.4 reported a false leak in 30–37% of histories, and a real player's rates can sit
there; the simulated players' non-leaks sit far below it. An ablation (200 resamples,
calling_station at 100 hands: v0.4.4 66%, v0.4.5 55%; without the design effect 61%;
without Benjamini–Hochberg 55%; without both 61%) shows the loss is spread over the
design effect, the multiplicity correction and the exact tests, with no single cause.
The trade was kept deliberately.

Other observations:

* Most injected tendencies are not detectable as leaks because the coach rarely flags
  them (over_folder, over_bluffer, slow_player, preflop_loose: 0% at every size). That
  matches the oracle, which finds no clear cost for any of them (§3).
* For calling_station almost every detected leak names a *river* concentration, although
  the deviation was injected on every street. This is real, not a statistical artefact:
  the coach confidently flags 71% of the injected river calls but only 33–40% on the flop
  and turn, where implied odds keep more verdicts at low confidence. The report's
  "condition not injected" line counts it as spurious; read it with that in mind.
* `beginner_style`, whose weaknesses are not injected, is reported as calling without
  the odds in 73% of 800-hand samples (v0.4.4: 89%), and the oracle confirms those calls
  are costly (report §4, ground-truth table).

**Monte Carlo error and reproducibility.** Each bootstrap cell uses 100 replicates, so a
detection percentage carries roughly ±10 points of resampling error (95%); treat
differences smaller than that as noise. The first full report used Python's `hash()` to
seed the bootstrap, which is randomised per interpreter, so two runs on identical
sessions gave different tables (e.g. river_station 11% vs 21%). Seeds are now derived with
CRC-32 from the run seed (`report.boot_seed`, tested across `PYTHONHASHSEED` values), and
two consecutive runs produce byte-identical `report.md` and `results.json`.
